## 1. Problem Statement & Motivation

During knowledge graph evaluation, automated edge alignment relies on a soft similarity threshold $\tau$ (e.g. cosine similarity or cross-encoder score $\ge 0.95$). Predicted relation triples that fall into the borderline uncertainty band:
$$\tau \in [0.80, 0.94]$$
frequently represent valid domain synonyms (e.g., predicted `EXPRESSES_FORCE` vs gold `HAS_GOVERNING_LAW`), legitimate paraphrases, or partial hallucinations.

In recent commits, the backend introduced `POST /api/evaluation/adjudications` and `GET /api/evaluation/adjudications`. However, two critical architectural gaps prevent the frontend workbench from delivering an effective Human-in-the-Loop (HITL) workflow:

1. **Absence of Pending Candidate Triage Queue:**
   `GET /api/evaluation/adjudications` only returns decisions that have *already been submitted*. There is **no endpoint to fetch the queue of pending, unadjudicated borderline candidates** generated by an evaluation run. The frontend cannot show the user what needs to be reviewed.
2. **Disconnected Metric Feedback Loop (No Dynamic Re-scoring):**
   When an expert reviews a candidate and marks it as `TRUE_POSITIVE` or `SCHEMA_ALIAS`, the current endpoint merely appends the decision to a JSON storage file. **It does not recompute the evaluation report**. The user cannot see how their curation affects Model Component Completeness (MCC), Property Fidelity (PFS), or overall $F_1$, defeating the purpose of an interactive curation workbench.

## 2. Functional Requirements

### 2.1 Domain Schema & Contracts (`episteme_studio.domain.evaluation`)

Extend domain contracts with queue items and recalculation payloads (strictly compliant with D-01):

```python
class AdjudicationQueueItem(BaseModel):
    candidate_id: str
    evaluation_id: str
    predicted_edge: dict[str, Any]       # {"source": "str:Law2", "predicate": "EXPRESSES", "target": "str:Mass"}
    reference_edge: dict[str, Any] | None # Candidate gold edge if partially matched
    similarity_score: float               # e.g., 0.865
    status: str                           # 'pending' or 'adjudicated'
    current_decision: AdjudicationDecision | None = None
    alias_target: str | None = None
    evidence_snippet: str | None = None   # Text quote or bounding box coordinates
    confidence: float = 1.0

class AdjudicationQueueResponse(BaseModel):
    evaluation_id: str
    total_candidates: int
    pending_count: int
    adjudicated_count: int
    candidates: list[AdjudicationQueueItem]

class AdjudicateAndRecalculateRequest(BaseModel):
    items: list[EdgeAdjudicationItem]
    export_dataset_path: str | None = None  # Optional path to export updated gold standard

class AdjudicateAndRecalculateResponse(BaseModel):
    evaluation_id: str
    adjudicated_count: int
    updated_report: EvaluationReportDetail
    metric_deltas: dict[str, float]       # e.g. {"f1": +0.035, "mcc": 0.0, "aor": -0.02}
    message: str = ""
```

### 2.2 Adapter & Service Implementation (`EvaluationAdapter` & `EvaluationService`)

1. **Extract Borderline Candidates During Evaluation:**
   - In `EvaluationAdapter.evaluate_run`, preserve all edge alignments whose soft similarity falls within configurable bounds (default $[\tau_{\text{min}}=0.75, \tau_{\text{max}}=0.95]$) in a run-scoped candidate cache `evaluation/candidates/{evaluation_id}.json`.
2. **Serve the Queue:**
   - Implement `get_adjudication_queue(evaluation_id, status, min_sim, max_sim)` in `EvaluationService`. If decisions already exist in `adjudications.json`, annotate the candidates with their current decision status (`pending` vs `adjudicated`).
3. **In-Place Dynamic Recalculation:**
   - Implement `adjudicate_and_recalculate(evaluation_id, request)`:
     - Register the new adjudication items via `save_adjudications`.
     - Re-evaluate the cached predicted graph against the gold dataset, treating `TRUE_POSITIVE` adjudications as verified matches and rewriting predicates for `SCHEMA_ALIAS` adjudications.
     - Compute the difference between original metrics and new metrics ($\Delta F_1, \Delta \text{MCC}$).
     - Overwrite the persisted `report_{evaluation_id}.json` and `report_{evaluation_id}.md`.
     - If `export_dataset_path` is specified, export the curated gold standard in JSON-LD format.

### 2.3 Studio API Endpoints (`episteme_studio.api.evaluation`)

Expose the new endpoints:
- `GET /api/evaluation/reports/{evaluation_id}/adjudication-queue`
  - Query parameters:
    - `status: str = 'pending'` (choices: `pending`, `adjudicated`, `all`)
    - `min_sim: float = 0.75`
    - `max_sim: float = 0.95`
  - Returns: `AdjudicationQueueResponse`
- `POST /api/evaluation/reports/{evaluation_id}/adjudicate-and-recalculate`
  - Body: `AdjudicateAndRecalculateRequest`
  - Returns: `AdjudicateAndRecalculateResponse` (HTTP 200)

### 2.4 Frontend UX Integration (`frontend/src/panels/`)
- Create `HITLAdjudicationWorkbench.tsx`:
  - Split-pane layout:
    - **Left:** Triage list of borderline candidate pairs sorted by similarity score with status tags (`Pending`, `Approved`, `Alias`).
    - **Right:** Comparison card displaying predicted triple vs reference triple, source text quote, and similarity breakdown.
    - **Action Bar:** Instant shortcut buttons:
      - `[✓ True Positive (A)]`
      - `[✗ False Positive (R)]`
      - `[⇄ Schema Alias (S)]` (reveals predicate selector dropdown)
      - `[Save & Update Score]`
  - Upon submission, display a celebratory toast with metric deltas: *"F1 score improved from 0.82 to 0.85 (+0.03)"*.

## 3. Acceptance Criteria

- [ ] `GET /api/evaluation/reports/{evaluation_id}/adjudication-queue` returns candidate edge pairs in the specified similarity interval.
- [ ] Submitting decisions via `POST /api/evaluation/reports/{evaluation_id}/adjudicate-and-recalculate` immediately re-scores the report in memory.
- [ ] Updated report reflects the verified matches, correctly adjusting precision, recall, and F1.
- [ ] Metric deltas ($\Delta \text{KPI}$) are returned in the API response.
- [ ] Persisted report JSON and Markdown files on disk reflect the updated scores.
- [ ] Unit tests in `test_evaluation_backend.py` verify queue retrieval, decision application, and score recalculation.
